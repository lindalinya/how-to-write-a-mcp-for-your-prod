# CLI / MCP 设计手册

一套针对 `mycli` 与 `mymcp` 的**设计拆解 + 实现教程 + 最佳实践规范**。

它不是产品使用手册，而是回答三个问题：

1. 这套系统**为什么**要这样设计？
2. 如果要**自己实现**一个类似的工具，该按什么顺序、遵守什么规则？
3. 哪些做法值得抄，哪些坑必须避开？

## 规范用语

本手册用 RFC 2119 风格的关键词：

- **必须（MUST）**：不遵守会出问题
- **应该（SHOULD）**：默认遵守，有充分理由才能偏离
- **可以（MAY）**：可选

## 证据来源与边界

本手册的结论来自三类证据：

| 证据类型 | 具体做法 | 可信度 |
|---|---|---|
| 二进制静态分析 | Go buildinfo、符号表、字符串常量、内嵌 SQL | 高（是事实） |
| 运行时验证 | 启动 MCP 服务发 JSON-RPC、执行只读命令、读取本地数据库 | 高（是行为） |
| 官方文档 | `docs/`、`README.md` | 中（是意图） |

**没有源码**。因此：

- 函数的具体实现细节是推断，不是事实
- 示意代码是按设计意图重写的，不是原始代码
- 标注"推断"的地方请自行验证

分析基准版本：

```
mycli   0.2.32
mymcp   0.2.12
launcher 0.10.0
Go        1.26 / 1.27
```

## 一句话总结

> 把 n 个 API 端点写一份带注解的规格，用同一份规格生成三种出口：
> 给人敲的命令、给脚本读的 JSON、给 AI 调的工具。
> 再叠加五层横切能力：版本适配、可靠传输、本地镜像、结构化输出、经验学习。
