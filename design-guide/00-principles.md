# 00 - 设计原则

十条贯穿 `wyn-cli` / `wyn-mcp` 的决策。每条都先讲**问题**，再讲**这套系统怎么解**，最后给**反例**。

---

## 原则 1：规格是唯一事实来源

**问题**：321 个 API 端点，如果每个都手写命令，命名会飘、参数会不一致、文档会过期。

**做法**：每个叶子命令都绑定三个注解：

```
pp:endpoint = "dashboards.create"
pp:method   = "POST"
pp:path     = "/api/v2/dashboards"
```

命令的用法、参数、帮助文本、MCP 工具定义、AI 提示词，全部从这条记录派生。

**判断标准**：新增一个接口时，你改的是**一条数据**，还是一段代码？
如果是后者，说明规格化没做到位。

**反例**：手写 300 个 `if cmd == "xxx"` 分支，半年后没人敢动。

---

## 原则 2：元数据同时服务多个消费者

**问题**：文档、权限、校验、AI 提示，各写一遍必然不一致。

**做法**：一条注解，多处消费。

| 注解 | 被谁消费 |
|---|---|
| `mcp:read-only` | MCP 的 `readOnlyHint`、文档警告、AI 决策 |
| `pp:requires-input` | 参数校验、AI 是否需要先问用户 |
| `pp:happy-args` | 帮助示例、AI 的默认参数建议 |
| `pp:deprecated` | 帮助文本、AI 应避免调用 |
| `pp:typed-exit-codes` | 脚本判断失败类型 |

**判断标准**：这条信息只在一个地方用吗？如果是，考虑是不是该升格成元数据。

**反例**：在代码里硬编码"这个接口是只读的"，然后在文档里再写一遍，然后 MCP 里再写一遍。

---

## 原则 3：给 AI 的接口要做减法

**问题**：把 321 个端点全暴露给 AI，模型会在 300 个相似选项里选错。

**做法**：MCP 只暴露 118 个工具。

筛选规律（实测）：

```
保留：高频、语义完整、能独立完成一件事的操作
砍掉：底层配置、碎片化接口、大部分管理类端点
优先：只读查询
```

**判断标准**：一个工具的名字，能不能让 AI 不看参数就知道该不该用？

**反例**：`get_user_by_id_and_org_with_options` 这种，AI 会疯。

---

## 原则 4：默认安全，危险操作必须显式解锁

**问题**：默认值决定了 90% 的使用场景。

**做法**：

| 场景 | 默认 | 解锁方式 |
|---|---|---|
| MCP 传输 | stdio（本地） | `--transport http` |
| HTTP 绑定 | `127.0.0.1:7777` | 显式指定 `--addr` |
| 非回环地址 | 拒绝启动 | 必须配 `--tls-cert` + `--tls-key` |
| HTTP 重定向 | 只允许公网 + 同协议 | 不提供关闭开关 |
| 发布 | dry-run 可先看 | `--dry-run` |

**判断标准**：一个新手什么都不配直接跑，会不会把危险面暴露出去？

**反例**：MCP 默认监听 `0.0.0.0:7777` 且无认证。

---

## 原则 5：每个"方便"都配一个"刹车"

**问题**：自动化跑起来之后，出问题往往是"太快""太多""重复"。

**做法**：成对设计。

| 方便的能力 | 配套刹车 |
|---|---|
| 全量同步 | `--max-age`（数据太旧才刷新）、`--max-pages` |
| 批量操作 | `--allow-partial-failure`、`--strict` |
| 自动重试 | `--idempotent`（需要幂等键） |
| 快速连续请求 | `--rate-limit`、自适应限流 |
| 本地缓存 | `--no-cache`、`--data-source live` |
| 自动学习 | `--no-learn`、`WYN_CLI_NO_LEARN=true` |

**判断标准**：这个能力出问题时，用户有没有一个开关能立刻关掉？

---

## 原则 6：自动学习必须有人工闸门

**问题**：AI 会把自己瞎猜的结论当成真理，越用越错。

**做法**：三隔离。

```
自动观察 → learn_candidates（隔离区，status=open）
         → 显式 confirm 才写入正式表
         → reject 打墓碑，同一签名永不再提
```

原文（二进制内）：

> Candidates are quarantined until an explicit `learnings confirm <id>` materializes them;
> they never alter command behavior or recall's verified results on their own.

**判断标准**：系统自己学到的知识，需不需要一个人点头才能生效？

**反例**：AI 每次调用都顺手写一条"经验"，下次直接拿来用。

---

## 原则 7：把用法写成协议，不是文档

**问题**：文档 AI 不一定会读，读了也不一定照做。

**做法**：`context` 工具返回 21KB JSON，里面是**可执行的行为规范**：

```json
{
  "instance_protocol": "1. 先确认目标实例 ... 2. 没有配置就默认 localhost:51980 ...",
  "learn_protocol": "1. Recall first: 回答领域问题前先查经验 ... 2. 空库短路 ...",
  "auth": {"type": "bearer_token", "env_vars": [...]},
  "compatibility": "9.1 可用 312/319 个端点"
}
```

**判断标准**：AI 第一次接触你的系统，能不能只靠一次工具调用就知道"该怎么用"？

---

## 原则 8：本地镜像换离线能力

**问题**：每次查询都打服务器，慢、费流量、断网就不能用。

**做法**：SQLite + FTS5 镜像。

```
sync → resources 表 + resources_fts（trigram 分词）
search / sql / analytics → 全部只读本地
--data-source auto | live | local → 显式选择数据来源
```

**判断标准**：断网时，查询类功能还能用吗？

**注意**：镜像会带来一致性问题和租户隔离问题，见 [05](05-storage-layer.md)。

---

## 原则 9：输出格式是产品的一部分

**问题**：同一条数据，人要看表格，脚本要 JSON，AI 要精简字段，导出要文件。

**做法**：输出管线独立于业务逻辑。

```
--json / --csv / --plain / --quiet / --human-friendly
--compact（只回关键字段）
--select id,name,status
--deliver file:out.json / webhook:https://...
```

**判断标准**：新增一个命令，输出层需要改吗？不需要才算解耦。

**为什么重要**：`--compact` 直接决定 AI 的 token 成本。

---

## 原则 10：错误要能指导动作

**问题**：一句 "failed" 什么也说明不了。

**做法**：错误必须携带"下一步"。

| 错误 | 携带的信息 |
|---|---|
| 版本不支持 | 哪些端点被门控、当前版本是多少 |
| 未认证 | 怎么配置 token（三条路径） |
| 限流 | 等多久、哪个端点类别 |
| 部分失败 | 成功几个、失败几个、要不要 `--strict` |
| 本地数据过期 | 多久前同步的、跑什么命令刷新 |
| 凭证是占位符 | 明确的配置文件路径 |

退出码也参与表达：

```
0  成功（或非关键失败，默认当警告）
2  参数/用法错误，或无匹配结果
```

**判断标准**：用户看到这条错误，能不能不查文档就知道下一步？
